# План задач

Документ основан на `README.md`. Анализ сделан по открытым движкам и их документации:
Bevy (Rust/wgpu, архитектура на плагинах), Fyrox (Rust), Godot (серверы подсистем),
O3DE (модульные Gems), Filament (мобильный PBR-рендер), а также Our Machinery, id Tech (CVar)
и Frostbite (Frame Graph, доклад GDC 2017).

## 0. Принятые решения

| #  | Решение | Следствия |
|----|---------|-----------|
| D1 | Весь движок на Rust, без C++ | Команда пришла из C++: в коде и документах поясняем неочевидные для C++ вещи и описываем используемые крейты |
| D2 | ECS — `bevy_ecs`, скрыт за модулем `engine::ecs` | Игровой код импортирует только `engine::ecs`. Если понадобится заменить ECS, правится один модуль |
| D3 | Графика: WebGPU, Vulkan, Metal + GLES3 (старые Android). WebGL2 не нужен | На Web работаем только через WebGPU. На тире GLES3 может не быть compute-шейдеров, поэтому фичи на compute идут с запасным путём или отключаются |
| D4 | И 2D, и 3D — выбор за проектом, а не за движком | 2D и 3D — отдельные плагины поверх общего ядра рендера. Проект подключает нужные |
| D5 | Мультиплеера нет. Нужен надёжный сетевой загрузчик (бинарные данные, модели, JSON, текстуры) | Отдельная подсистема `engine_net` в итерации 1: таймауты, повторы, дедупликация запросов, дисковый кеш (раздел «Сеть») |
| D6 | Полноценный редактор — после отладки движка | Рефлексия и сериализация закладываются в итерации 2, чтобы редактор было на чём строить |

## 1. Оценка предложенного набора систем

### Что стоит переосмыслить

- **«Система работы с памятью»** — в Rust это не отдельная подсистема. Нужен набор утилит в `core`:
  кадровый аллокатор (arena, сбрасывается каждый кадр), пулы и slot-map'ы для хэндлов,
  бюджеты памяти ресурсов. Глобальный аллокатор заменяется одной строкой (mimalloc).
- **«Логирование и тестирование»** — тестирование не рантайм-система, это инфраструктура (CI).
  Логирование объединить с профилированием: оба строятся на `tracing`.
- **«Парсеры файлов»** — это загрузчики ресурсов, часть системы ресурсов, а не отдельная система.
- **«Граф сцены»** — при наличии ECS отдельная структура дерева не нужна:
  иерархия = компоненты `Parent`/`Children` + система распространения трансформов.
  Два источника правды (ECS и граф) — частый источник багов.
- **«Система событий»** — глобальная шина с колбэками плохо дружит с Rust (заимствования, порядок вызовов).
  Лучше типизированные очереди событий с двойной буферизацией, читаемые системами ECS.
- **«Многопоточность»** — на Web потоков по умолчанию нет (нужны SharedArrayBuffer и заголовки COOP/COEP).
  Пул задач обязан иметь однопоточный режим, иначе Web не заработает.
- **«Глубокая оптимизация»** — без профилирования это гадание. Предлагаем вместо этого: бюджеты кадра
  на каждую платформу, профайлер с первого дня, бенчмарки в CI, data-oriented дизайн по умолчанию.

### Чего не хватает в списке

| Система | Зачем |
|---------|-------|
| Платформа / окно / жизненный цикл приложения | Android и iOS уничтожают surface при сворачивании — без обработки приложение падает. На Web свой цикл кадров |
| Ядро приложения: плагины, планировщик систем, время, игровой цикл | Именно это даёт «удобно расширять». Фиксированный шаг для физики |
| Конфигурация через CVar (переменные консоли) | Одна система закрывает три требования: конфиг при запуске, аргументы командной строки и чит-консоль |
| Рефлексия и сериализация | Нужна для сцен, сохранений, консоли, отладочного UI и будущего редактора |
| Шейдеры | WGSL, препроцессор/модули (`naga_oil`), перестановки (permutations), кеш пайплайнов |
| Управление GPU-ресурсами | Пулы буферов, кеш bind group, staging-загрузка, учёт видеопамяти |
| Render graph (frame graph) | Основа для теней, постэффектов, рендер-таргетов и offscreen. Без него каждая новая фича ломает соседей |
| Отладочный UI | `egui` — быстрый способ показать статистику, консоль, инспектор |
| Офлайн-пайплайн ресурсов («cook») | На мобилках и Web нельзя грузить PNG/OBJ: нужны KTX2/Basis, сжатые меши. Делается позже, но формат закладывается сразу |
| Горячая перезагрузка ресурсов (desktop) | Сильно ускоряет разработку шейдеров и контента |

## 3. Итерации

- **Итерация 0 — фундамент.** Репозиторий, сборка и CI на всех 5 платформах до первой строки движка.
  Портирование «потом» — самая дорогая ошибка в кроссплатформенных движках.
- **Итерация 1 — минимальный движок. ✅ Закрыта 2026-11-13.** На всех платформах — освещённые
  glTF-модели, offscreen-рендер, профайлер, переменные конфигурации, отладочный UI, тест картинок.
  Остатки частично сделанных задач перенесены в итерацию 2 (что нужно её фичам) или в раздел
  «По требованию» (делаем, когда появится реальная нужда или данные профайлера).
- **Итерация 2 — важные системы.** Тени, освещение, текст, постэффекты, анимация, аудио, физика, консоль.
- **Итерация 3 — позже.** Всё тяжёлое и не блокирующее.
- **По требованию** — задачи без срока: берём, когда они станут нужны.
- **Проверки на устройствах** — то, что не проверить на эмуляторах и в CI.

Статусы: ✅ — сделано; «→ X» — остаток перенесён в задачу X.

работает так же, как загрузка с диска.
