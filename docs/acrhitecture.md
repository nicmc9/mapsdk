# Архитектура движка

Документ фиксирует принятые решения. Требования — в `README.md`, задачи — в `task.md`.
Команда пришла из C++, поэтому неочевидные для C++ вещи помечены как **[Rust]**.

---

## 1. Ключевые решения

| Тема | Решение |
|------|---------|
| Язык | Только Rust, без смешивания с C++ |
| Графика | `wgpu`. Тиры: WebGPU / Vulkan / Metal (основной) и GLES3 (старые Android). WebGL2 не поддерживаем |
| Платформы | macOS, Linux, Android, iOS, Web (wasm) |
| ECS | `bevy_ecs` за модулем `engine::ecs` |
| 2D / 3D | Оба, как отдельные плагины. Выбирает проект |
| Потоки | Отдельный поток рендера с первой итерации |
| Логика | Фиксированный шаг + интерполяция в рендере |
| Сеть | Мультиплеера нет. Надёжный загрузчик данных с кешем |
| Редактор | После отладки движка. Рефлексия закладывается заранее |

## 2. Слои и зависимости

```
┌──────────────────────────────────────────────────────────────┐
│ Проект (игра / приложение)                                   │
├──────────────────────────────────────────────────────────────┤
│ Плагины уровня 2: engine_3d, engine_2d, анимация, физика,    │
│                   аудио, текст, постэффекты, консоль, UI     │
├──────────────────────────────────────────────────────────────┤
│ engine_render  (render graph, GPU-ресурсы, шейдеры, offscreen)│
├──────────────────────────────────────────────────────────────┤
│ engine_assets   engine_net   engine_ecs   engine_input       │
├──────────────────────────────────────────────────────────────┤
│ engine_core  (App, плагины, расписание, время, события,      │
│               потоки и каналы, CVar, логи, профилирование)   │
├──────────────────────────────────────────────────────────────┤
│ engine_platform (окно, жизненный цикл, VFS-источники)        │
│ engine_math     (псевдонимы на glam, геометрия)              │
└──────────────────────────────────────────────────────────────┘
```

- Зависимость идёт только вниз. Нижний слой ничего не знает о верхнем.
- Каждый блок — отдельный крейт в Cargo workspace. Фасадный крейт `engine` реэкспортирует их.
- **[Rust]** Cargo запрещает циклические зависимости между крейтами. Нарушение слоёв — ошибка
  сборки, а не вопрос дисциплины, как с CMake-таргетами.
- **[Rust]** Ненужные подсистемы отключаются feature-флагами Cargo (`features = ["physics"]`).
  Это аналог `#ifdef` + опций CMake, но на уровне зависимостей. Важно для размера wasm.

### Плагины — единица расширения

```rust
// Подсистема регистрирует всё своё: ресурсы, системы, загрузчики, CVar'ы.
pub trait Plugin {
    fn build(&self, app: &mut App);
}

App::new()
    .add_plugin(CorePlugin)
    .add_plugin(RenderPlugin::default())
    .add_plugin(Render3dPlugin)
    .run();
```

**[Rust]** `trait` — это не базовый класс. Наследования данных нет, есть только набор методов,
которые тип обязуется реализовать. Ближайшие аналоги в C++ — интерфейс с чисто виртуальными
методами или concept. Вызов может быть статическим (`impl Plugin`, как шаблон) или динамическим
(`Box<dyn Plugin>`, как виртуальный вызов).

### Замена сторонних библиотек

| Уровень | Как | Пример |
|---------|-----|--------|
| Математика | Псевдоним типа | `pub type Vec3 = glam::Vec3;` (аналог `using`) |
| Тяжёлые бэкенды | Трейт-фасад + реализация в отдельном крейте | `engine_physics` + `engine_physics_rapier` |
| `wgpu` | Не оборачиваем повторно | Типы `wgpu` не выходят за пределы `engine_render` |

---

### ECS за модулем `engine::ecs`

Проект пишет `use engine::prelude::*;` и не зависит от `bevy_ecs` напрямую.

**[Rust]** Нюанс derive-макросов. `#[derive(Component)]` генерирует код с путём `bevy_ecs::...`
и ищет крейт `bevy_ecs` в `Cargo.toml` проекта. Его там нет, поэтому `engine::ecs::prelude`
реэкспортирует сам `bevy_ecs`: имя попадает в область видимости вместе с `use ...prelude::*`.
Без этого импорта derive-макросы ECS не скомпилируются.

## 3. Потоки

```
┌──────────── Главный поток ────────────┐        ┌──────── Поток рендера ────────┐
│ ОС-события (winit), ввод, жизненный   │        │ Данные для отрисовки, wgpu,   │
│ цикл, логика (ECS, фиксированный шаг) │        │ загрузка в GPU, present       │
│                                       │        │                               │
│ [ящик MainEvent]  ◄──── события ──────┼────────┤                               │
│                   ───── команды ──────┼───────►│ [ящик RenderCommand]          │
│ продюсер ═══ тройной буфер ═══════════┼═══════►│ консьюмер                     │
└───────────────────────────────────────┘        └───────────────────────────────┘
        ▲                       ▲
┌───────┴─────────┐   ┌─────────┴──────────────────┐
│ Пул воркеров    │   │ Ввод-вывод (async): сеть,  │
│ (системы ECS,   │   │ диск, декодирование        │
│ тяжёлые задачи) │   │ ресурсов                   │
└─────────────────┘   └────────────────────────────┘
```

| Поток | Владеет | Почему так |
|-------|---------|------------|
| Главный | Окно, цикл событий, ECS-мир логики | На iOS и macOS события окна приходят только в главный поток. Отдельный поток для логики почти ничего не даёт: системы ECS и так распараллеливаются на воркерах |
| Рендер | Device/Queue `wgpu`, surface, все GPU-объекты, мир рендера | Отрисовка не тормозит логику, логика не тормозит отрисовку |
| Воркеры | Ничего постоянного | Параллельные системы ECS, разовые тяжёлые задачи |
| Ввод-вывод | Сетевые соединения, файлы | Асинхронные операции не блокируют кадр |

### Режимы запуска рендера

| Режим | Где | Как |
|-------|-----|-----|
| `Threaded` | macOS, Linux, Android, iOS | Рендер в своём потоке |
| `Inline` | Web; отладка на любой платформе | Тот же код рендера вызывается в главном потоке после логики |

Зачем нужен `Inline`:
1. В wasm по умолчанию нет потоков.
2. На Web объекты `wgpu` — это JS-объекты, привязанные к своему потоку.
   **[Rust]** Там они не `Send`, и передать их в другой поток не даст компилятор.

Как это сделано:
- Surface создаётся **в главном потоке** (на macOS и iOS со слоем окна можно работать только
  из него) и командой `SurfaceCreated` передаётся рендеру. Адаптер и устройство рендер создаёт сам.
- Инициализация GPU асинхронная (`Future`). Рендер опрашивает её каждый кадр, без исполнителя:
  на native она завершается сразу, в браузере ждёт промис.
- В режиме `Threaded` рендер рисует с частотой экрана (vsync через `PresentMode::Fifo`),
  независимо от логики. В режиме `Inline` — один кадр рендера на кадр главного цикла.
- На Web главный цикл идёт от `requestAnimationFrame` (`NextUpdate::NextDisplayFrame`), а не от
  таймеров: таймеры браузера неточны и замедляются в фоновой вкладке.
- Синхронные события платформы (окно появилось, уход в фон, размер, выход) рендер получает
  через `App::add_lifecycle_hook` — сразу, а не в следующем кадре ECS.

Оба режима используют одни и те же каналы и тройной буфер. Разница только в том, кто вызывает
`render_frame()`. Код рендера не должен знать, в каком режиме он работает.

## 4. Общение между потоками

Есть два вида данных и для каждого свой механизм. Смешивать их нельзя.

| | Состояние кадра | События и команды |
|---|---|---|
| Пример | Трансформы, камера, свет, позы скелетов | «Создать текстуру», «surface потерян», «ресурс загружен» |
| Если потерять | Не страшно: следующий кадр перезапишет | Ошибка: текстура никогда не появится |
| Важно | Последнее значение | Каждое сообщение и порядок |
| Механизм | **Тройной буфер** | **Почтовый ящик потока** |

### 4.1 Тройной буфер (продюсер — логика, консьюмер — рендер)

```
 продюсер пишет      обмен через атомик      консьюмер читает
   [ back ]  ──publish──►  [ middle ]  ──take──►  [ front ]
```

- Три слота. Продюсер пишет только в `back`, консьюмер читает только `front`.
  Никто никого не ждёт, мьютексов нет.
- `publish` атомарно меняет `back` ↔ `middle` и ставит флаг «есть новое».
  `take` при наличии флага меняет `middle` ↔ `front`.
- Правило «побеждает последний»: промежуточный снимок может быть перезаписан. Поэтому через
  тройной буфер идёт **только состояние**, никогда не команды.
- Слоты переиспользуются. `Vec` внутри очищаются через `clear()`, ёмкость сохраняется,
  и в установившемся режиме аллокаций за кадр нет.
- Реализация: крейт `triple_buffer` (готовый lock-free, без зависимостей) или своя на атомиках.
  **[Rust]** `AtomicUsize` и `Ordering::Acquire/Release` работают так же, как `std::atomic`
  и `memory_order` в C++.

Постоянные объекты (меш, материал, текстура) **не** копируются в каждый снимок. Они создаются
и удаляются командами, а снимок содержит только их `RenderId`.

```rust
pub struct FrameSnapshot {
    pub sim_time: f64,          // время шага логики, для интерполяции
    pub camera: CameraData,
    pub draws: Vec<DrawItem>,   // clear() каждый кадр
}

pub struct DrawItem {
    pub mesh: RenderId,
    pub material: RenderId,
    pub prev_transform: Mat4,   // трансформ на предыдущем шаге логики
    pub transform: Mat4,        // трансформ на текущем шаге
}
```

### 4.2 Почтовые ящики (события и команды)

У каждого потока своя входящая очередь. Отправлять в неё может кто угодно, разбирает только
владелец — в удобный ему момент, обычно в начале кадра.

```rust
// Сообщения для рендера. enum с данными — аналог std::variant, но match
// обязан обработать все варианты: забытый случай — ошибка компиляции.
pub enum RenderCommand {
    CreateTexture { id: RenderId, desc: TextureDesc, pixels: Vec<u8> },
    DestroyTexture(RenderId),
    Resize { width: u32, height: u32 },
    SurfaceLost { reply: oneshot::Sender<()> },
    ReadbackFrame { reply: oneshot::Sender<Image> },
    Shutdown,
}

// Рендер в начале кадра забирает всё накопившееся, не блокируясь
while let Ok(cmd) = inbox.try_recv() {
    match cmd { /* ... */ }
}
```

- **[Rust] Отправка перемещает владение.** Для `pixels: Vec<u8>` копируются 24 байта
  (указатель, длина, ёмкость), а не сами пиксели. После `send` отправитель не может обратиться
  к вектору — это ошибка компиляции. В C++ после `std::move` объект остаётся доступным,
  и use-after-move компилируется.
- **[Rust] `Send` / `Sync`.** Компилятор пропускает в канал только потокобезопасные типы.
  `Rc` (непотокобезопасный счётчик ссылок) в другой поток не отправить, программа не соберётся.
- **`oneshot`** — одноразовый канал «запрос → один ответ», аналог `std::promise`/`std::future`.
- **Очереди неограниченные.** Две ограниченные очереди, в которые потоки блокирующе пишут
  друг другу, приводят к deadlock. Длина очередей выводится в статистику, при росте — предупреждение.
- **Крейт `crossbeam-channel`** — быстрые MPMC-очереди с `select!` (ожидание на нескольких
  каналах сразу). `std::sync::mpsc` тоже есть, но без `select`.
- **Пробуждение главного потока.** Он спит внутри цикла событий winit, поэтому его будят через
  `EventLoopProxy::send_event`, штатный механизм winit.

### 4.3 Синхронные запросы

Обычно потоки друг друга не ждут. Исключения, где ждать обязательно:

| Ситуация | Почему |
|----------|--------|
| Потеря surface (сворачивание на Android/iOS) | Главный поток должен дождаться ответа «surface отпущен» и только потом вернуть управление ОС. Иначе рендер обратится к уничтоженному окну |
| Завершение работы | `Shutdown` → ожидание окончания потока (`join`) |
| Чтение кадра в offscreen-режиме | Ответ приходит через `oneshot`, ждёт тот, кто запросил |

## 5. Кадр: фиксированный шаг и интерполяция

Логика работает с фиксированным шагом `dt` (по умолчанию 60 Гц, задаётся CVar `sim.hz`).
Рендер рисует с частотой экрана и интерполирует между двумя последними шагами логики.

```
Главный поток, каждый проход цикла:
  1. Разобрать ОС-события и свой ящик
  2. Ввод, UI, всё, что зависит от частоты кадров
  3. accumulator += реальное время с прошлого прохода
     while accumulator >= dt { fixed_update(); accumulator -= dt; }
     (ограничение числа шагов за проход защищает от «спирали смерти»)
  4. Если был хотя бы один шаг — заполнить снимок и publish

Поток рендера, каждый кадр:
  1. Разобрать свой ящик (создание/удаление GPU-объектов, resize...)
  2. take() свежего снимка (или работа с предыдущим, если нового нет)
  3. alpha = (render_time - (sim_time - dt)) / dt, ограничить [0, 1]
     transform = interpolate(prev_transform, transform, alpha)
  4. Отсечение, render graph, отправка в GPU, present
```

- Плавное движение на 120/144 Гц экранах при логике 60 Гц, детерминированная физика.
- Цена — задержка до одного шага логики. Камеру при необходимости можно обновлять не на
  фиксированном шаге, а в пункте 2, чтобы управление ощущалось мгновенным.
- Главный поток спит до момента следующего шага (`ControlFlow::WaitUntil`). События ОС будят его
  раньше, но кадр выполняется только по расписанию — иначе частота кадров зависела бы от того,
  как активно пользователь двигает мышью.
- В фоне кадры не выполняются, а время, проведённое в фоне, не попадает в логику:
  после возврата первый кадр получает нулевой `delta`.
- Сообщения ECS о жизненном цикле (`AppLifecycle::Suspended`) системы прочитают только
  в следующем кадре, то есть уже после возврата из фона. Всё срочное (остановка рендера
  перед уничтожением окна) делается в синхронном вызове `PlatformHandler::suspended`, а не через ECS.
- `prev_transform` хранится в самом `DrawItem`, а не в предыдущем снимке. Тогда рендеру не нужно
  держать два снимка и сопоставлять их. Новый объект получает `prev_transform = transform`.

## 6. Ссылки между объектами

| Что | Чем ссылаемся | Аналог в C++ |
|-----|---------------|--------------|
| Объект сцены | `Entity` (индекс + поколение) | id в `entt` |
| Ресурс | `Handle<T>`: сильный держит ресурс, слабый — нет | `shared_ptr` / `weak_ptr`, но без указателя |
| GPU-объект на стороне рендера | `RenderId` | `FRHIResource*` в Unreal, но как индекс |

- Обычные ссылки `&T` живут только внутри одного вызова. Хранить `&T` в полях структур
  между кадрами запрещено.
- **[Rust]** Это не стилистика. Структура с полем `&T` обязана иметь параметр времени жизни
  (`struct Foo<'a> { x: &'a T }`). Компилятор следит, чтобы ссылка не пережила объект,
  и для долгоживущих графов объектов это быстро становится неуправляемым. Индекс + поколение
  снимают проблему.
- Поколение делает «висячий» id безопасным: обращение к удалённому объекту вернёт `None`,
  а не мусор из памяти.
- Иерархия сцены — компоненты `Parent`/`Children` в ECS. Отдельного графа сцены нет.

## 7. Ресурсы

```rust
let helmet: Handle<Gltf> = server.load("models/khronos/DamagedHelmet/DamagedHelmet.glb");
// ... позже, в системе:
if let Some(resolved) = gltfs.get(&helmet) { /* resolved.asset, resolved.status */ }
```

- `AssetServer::load` сразу возвращает хэндл. Тот же путь и тип — тот же ресурс.
- Загрузка идёт в задаче пула IO: чтение через VFS → загрузчик формата. Результат
  применяется в начале кадра (стадия `First`), системы видят его через `Assets<T>` и
  событие `AssetEvent<T>`.
- **Загрузчик** (`AssetLoader`) асинхронный: может дочитать соседние файлы (`ctx.read`),
  запросить зависимость (`ctx.load`) и создать вложенный ресурс с меткой (`ctx.add_labeled`,
  путь `файл.glb#Mesh0`). Вложенный ресурс можно запросить и до загрузки файла.
- **Хэндл**: индекс + поколение + счётчик ссылок (`Arc`). Когда исчезает последний сильный
  хэндл, ресурс выгружается в начале следующего кадра; хэндлы внутри него (меши glTF)
  исчезают вместе с ним — выгрузка каскадная.
- **Подстановки**: `loading_fallback` / `error_fallback` у типа ресурса. Для `Image` —
  серый пиксель и розово-чёрная «шахматка» 8×8.
- **Ошибки**: статус `Failed` с причиной, событие `AssetEvent::Failed`, строка в логе.
  CVar `assets.strict` превращает ошибку в панику (CI, тесты).
- **[Rust] Стирание типов.** Сервер хранит загрузчики и операции над ресурсами разных
  типов в одних коллекциях: трейт без параметра типа (`ErasedLoader`) и указатели на
  обобщённые функции (`apply_loaded::<T>`), по одной на тип. В C++ это сделали бы базовым
  классом с виртуальными методами.
- **[Rust] Зоны профайлера в async-коде** — `.instrument(span)`, а не `entered()`:
  охранник зоны нельзя держать через `.await`, задача может продолжиться в другом потоке.

## 8. Файлы и сеть

| Путь | Платформа | Источник |
|------|-----------|----------|
| `http(s)://...` | все | сеть (`engine_net`) |
| относительный | macOS, Linux | папка `assets.root` (по умолчанию `assets`) |
| относительный | Web | HTTP: `assets.root` + путь, относительно страницы |
| относительный | iOS | папка `assets` внутри `.app` |
| относительный | Android | assets внутри APK |

Сетевой загрузчик (`engine_net`):
- native — `ureq` (блокирующий вызов в потоке пула IO), Web — `fetch`;
- таймауты и повторы с растущей задержкой — CVar `net.*`;
- одновременные запросы одного URL — одна загрузка (`futures_util::Shared`);
- дисковый кеш (native): `<кеш ОС>/mapsdk/net`, лимит `net.cache_max_mb`, вытеснение по
  времени доступа, условные запросы (`ETag` → 304), при недоступной сети — старая копия;
- Web: кешем управляет браузер.
- **[Rust]** На Web future `fetch` держит JS-объекты и не может быть `Send`, а ресурс ECS
  обязан быть `Send`. В wasm без атомиков потоков нет, поэтому future обёрнут в `WasmSend`
  с `unsafe impl Send` — обещание проверяется условием компиляции.

## 9. Ошибки

- Ожидаемые ошибки (файл не найден, таймаут сети, битый формат) — это `Result<T, E>`,
  пробрасываются оператором `?`. Для ресурсов ошибка превращается в статус `Failed` и подстановку.
- `panic!` — только нарушение инвариантов, то есть баг в коде.
- **[Rust]** Исключений нет. `?` — это сокращение для «если ошибка, вернуть её из функции».
  Ошибка видна в сигнатуре функции, проигнорировать `Result` без явного действия
  компилятор не даст (предупреждение `unused_must_use`, в CI — ошибка).
- Типы ошибок подсистем: `thiserror` (удобное объявление enum ошибок). В примерах и
  инструментах — `anyhow` (ошибка «любого типа» с контекстом).

## 10. Конфигурация (CVar)

```rust
// Объявление — рядом с кодом, который использует значение
pub static SIM_HZ: CVar<f64> = CVar::new("sim.hz", 60.0, "Частота шага логики, Гц");

// Регистрация — в Plugin::build
app.register_cvar(&SIM_HZ);

// Чтение — из любого потока, без доступа к ECS
let hz = SIM_HZ.get();
```

- Типы значений: `bool`, целые, `f32`/`f64`, строки (`CVarString`) и любой свой тип с трейтом
  `CVarValue` (так сделан `render.mode`).
- Источники по возрастанию приоритета: значение по умолчанию → файл TOML
  (`App::load_config_toml`) → аргументы запуска (`--cvar имя=значение`, на Web `?имя=значение`) →
  консоль. Значения для ещё не зарегистрированных переменных запоминаются и применяются при
  регистрации. После старта неизвестное имя — предупреждение («опечатка?»).
- Флаги: `STARTUP` — после старта из консоли не меняется; `CHEAT` — только при `cheats = true`.
- Изменения на лету система замечает по `version()`: сравнивает с сохранённой и применяет
  (так работают `sim.hz` и `log.filter`).
- **[Rust]** Статических конструкторов нет: код до `main` не выполняется, поэтому переменная не
  может зарегистрироваться сама, как глобальный объект в C++. Регистрация всегда явная.

## Логи и профилирование

- Логи — `tracing`. Вывод выбирается под платформу: stderr, logcat, `os_log`, консоль браузера.
  Фильтр — CVar `log.filter` (синтаксис `RUST_LOG`), меняется на лету.
- Зоны профайлера — спаны `tracing` уровня `trace`:
  `let _zone = tracing::trace_span!("name").entered();`. В логи они не попадают, а без фичи
  `profiling` почти ничего не стоят.
- `cargo run -p sandbox --features engine/profiling` — данные идут в Tracy. Размечены кадр, стадии,
  каждая система ECS, кадр рендера, ожидание кадра экрана, отправка на GPU. У главного потока
  и потока рендера свои шкалы кадров.

## 11. Рендер

- Тиры возможностей определяются при старте. Фичи, которым нужны compute-шейдеры,
  на GLES3 получают запасной путь или отключаются.
- Render graph описывает проходы и их ресурсы. Порядок и барьеры вычисляются автоматически.
- Цель отрисовки — `Surface` (окно) или `Texture` (offscreen). Offscreen — это запуск без окна
  и чтение пикселей через `ReadbackFrame`. На нём же строятся golden-image тесты в CI.
